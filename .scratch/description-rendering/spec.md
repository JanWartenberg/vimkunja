# Rich-Text Description Contract (Draft)

> This document defines Vimkunja's durable contract for reading, displaying, editing, and saving Vikunja Task Descriptions. It deliberately outlives the originating ticket: the contract may later inform terminal rich-text work outside Vimkunja, but it is currently specific to Vimkunja and does not define a new markup language.

**Related tickets:** M2 reader: [01 — Render Vikunja HTML descriptions as readable terminal text (archived)](../../.archive/2026-08-05/description-rendering/issues/01-render-vikunja-html-descriptions.md); M3 structured reader/editor: [02 — Specify native Rich-Text Description rendering and editing](issues/02-specify-native-rich-text-description-rendering-and-editing.md)

**Companion artifacts:** [Keybinding Contract](../../docs/keybindings.md), [TUI/Rich-text glossary](../../CONTEXT.md), [Vim Visual-Mode binding review](research-vim-visual-bindings.md), [Task Detail Done toggle](../task-detail-done-toggle/issues/01-toggle-task-done-from-detail-pane.md), [deferred Checkbox-list summary](../checkbox-list-progress-summary/issues/01-show-checkbox-list-progress-summary.md), and [deferred independent Link label/URL editor](../link-label-and-url-editor/issues/01-evaluate-independent-link-label-url-editing.md).

## Purpose

Vikunja stores rich-text Task Descriptions as HTML. Vimkunja must provide a keyboard-first terminal editing experience without exposing HTML source for normal editing, while continuing to store Vikunja-compatible HTML and without changing the database schema.

## Terms

- **Source HTML:** HTML read from and written to Vikunja's existing `tasks.description` field.
- **Description document:** Vimkunja's structured interpretation of Source HTML for rendering and editing.
- **Terminal projection:** The keyboard-navigable, terminal-appropriate rendering of a Description document. It need not be visually identical to the web application.
- **Description block:** A logical block in a Description document, such as a paragraph, heading, list item, code block, quote, or table.
- **Checkbox list:** A checklist embedded in a Description, represented by Vikunja/Tiptap `data-type="taskList"` HTML. This is distinct from Vimkunja's Tasks Pane and its Task records.
- **Native node:** A safely parsed Description structure that Vimkunja understands and can edit through its Terminal projection.
- **Opaque subtree:** The outermost safely parsed Description structure that Vimkunja cannot edit internally. It is one atomic unit whose original HTML is preserved during unrelated edits.
- **Blocked Description:** A Description whose Source HTML is malformed, unsafe, or cannot be preserved reliably, so structured editing and saving remain disabled until explicit recovery.

## Agreed principles

1. Source HTML remains the persistence format. Vimkunja does not store an alternative format or change Vikunja's schema.
2. Normal editing must not require the user to read or edit HTML source.
3. M2's completed reader-only phase uses a deliberately lossy HTML-to-plain-text projection for display. It never writes Source HTML. Native rendering, editing, and saving use a structured document model rather than lossy conversion.
4. Existing opaque subtrees must not be changed by an unrelated edit. The outermost opaque ancestor is one atomic subtree; its descendants may contribute to its safe projection but are not independently focused, selected, edited, or validated. More generally, Vimkunja preserves every safely parseable existing Source HTML structure and attribute unless an explicit, accepted rule permits a semantic rewrite; surprising data loss is not an acceptable normalization.
5. Unsupported terminal presentation degrades to readable content; it must not display literal markup merely because it is unsupported. Unknown parseable HTML renders its text contents recursively without special formatting; structurally empty unsupported content displays a neutral unsupported-content hint.
6. Native terminal formatting is semantic where possible. Terminal capabilities may affect visual fallback, but not the document's HTML meaning.
7. Paragraphs and other Description blocks are parsed from Source HTML even when that HTML is stored as one long string. The Terminal projection separates logical blocks for navigation; it does not navigate HTML source text.
8. Saving uses hybrid serialization: Native nodes become compact, canonical HTML under the semantic rules below, while every retained Opaque subtree preserves its original Source HTML byte-for-byte. Presentation-only indentation and line breaks are never added between Native elements.
9. In a Description, `j` and `k` jump between navigable logical blocks: paragraphs, headings, and individual list or Checkbox-list entries. `gj` and `gk` move between visual terminal rows created by soft-wrapping a navigable text block.
10. Checkbox lists are part of the first native editable subset. Vimkunja can add and remove their entries and toggle their checked state. This changes only the Description document's `data-checked` state, never the enclosing Task record's Done status. On every successful Description save, Vimkunja assigns a unique lowercase UUID v4 `data-task-id` to every Checkbox entry that lacks one. Existing unique IDs, including non-UUID values, are not regenerated, and subsequent saves retain each generated ID. Before saving duplicate nonempty IDs, Vimkunja asks whether to deduplicate them. Confirmation preserves the first occurrence in document order, assigns fresh non-colliding lowercase UUID v4 values to later occurrences, and continues the save; cancellation aborts the save and leaves the draft unchanged. Duplicating an entry through Vimkunja always creates a fresh ID rather than copying the original entry's ID.
11. Headings `h1` through `h3` are part of the first native editable subset.
12. Bold, italic, underline, and strikethrough are part of the first native editable subset. Their terminal projections may use capability-dependent visual fallbacks without changing their HTML meaning. HTML's semantic distinctions remain part of the Native model even when the terminal style is identical: imported `<b>` remains distinct from `<strong>`, and imported `<i>` remains distinct from `<em>`. New Vimkunja bold and italic formatting serializes as `<strong>` and `<em>`; obsolete imported `<strike>` normalizes to `<s>`. Nested `<strong>` and `<em>` depth is semantically significant and must not be flattened.
13. Ordered and unordered lists are part of the first native editable subset. Nested lists are rendered and preserved in V1. Their existing text and Checkbox-list state remain editable, but native indentation, outdent, and other structural nesting edits are deferred.
14. Code blocks are part of the first native editable subset. They use a theme-configurable background across the entire block plus a thin presentation-only `│` prefix as a non-color fallback. Multi-line Code blocks preserve every source character, including indentation, tabs, blank lines, and a final trailing newline, without soft wrapping or serialization normalization; overwide code scrolls horizontally with `zh`/`zl` and shows a one-row, non-editable scrollbar inside the block only while content overflows.
15. Block quotes are part of the first native editable subset. A Block quote is HTML `<blockquote>`, an extended quotation distinct from inline `<q>`. Its first visual row has the presentation-only prefix `│  ` and wrapped continuation rows have `│↪ `; ASCII fallbacks are `|  ` and `|> `. Nested quotes add one prefix per depth. Prefixes are never cursor targets or editable in either mode, and no quote-specific background or color is required. A quote contains any native editable Description blocks, including nested quotes and Code blocks. Parseable existing `cite` and VOA `data-comment-id` attributes are preservation-only: Vimkunja carries them through safe unrelated edits but offers no M3 input or editing UI or Task-Description reply semantics.
16. Horizontal rules are part of the first native editable subset. A rule is an atomic, selectable Description block. In Normal Mode, `dd` deletes the whole rule block. `x` deletes one displayed dash at a time; once fewer than three dashes remain, the content becomes ordinary paragraph text. Visual selection editing may be added in a future iteration.
17. Links are part of the first native editable subset. Their terminal editing flow operates on visible link text and a separate URL, never on raw `<a>` markup. Links render as their visible label, with underline/color when supported and without an inline URL. With the cursor inside a link, the status/footer shows `Link → URL · typing extends link · Space+l edit`; immediately at a link edge it instead says `Link edge → URL · typing is outside link`. `Space+l` opens the URL prompt. `Space+l` in Visual Mode applies a prompted URL to the selected text; in Description Normal Mode with a cursor inside an existing link, it prompts with the existing URL. Link text remains ordinary editable Description text. Text inserted inside an existing link remains linked; text inserted exactly before or after it remains ordinary text, so extending a link requires explicitly selecting the desired text and applying `Space+l`. An empty URL removes the link. M3 accepts only VOA's absolute `://` URL schemes—`http`, `https`, `ftp`, `git`, `obsidian`, `notion`, and `message`—and rejects relative, schemeless, and other URLs while keeping the prompt open with a clear error. The allowed-scheme policy must be centralized and deliberately extensible for a future approved tool/protocol extension, rather than embedded across editor flows. M3's allowlist is fixed: a future extension must explicitly approve a new protocol through its own configuration or extension contract; unknown imported schemes do not become newly creatable merely by appearing in existing data. Every serialized Native Link uses Vikunja's `target="_blank"` behavior, including an imported Link that originally omitted `target` or used another target. New or edited Links emit canonical `href` and `target="_blank"`; safe, meaningful imported attributes such as `title`, `rel`, and compatible data attributes are preserved semantically, without preserving attribute order or quoting. Vimkunja does not invent `rel="noopener"` when it is absent. Unsafe or ambiguous Link attributes make the Description Blocked rather than being silently dropped. Link labels may freely combine bold, italic, underline, strikethrough, and hard breaks; serialize their formatting inside the `<a>` element in canonical form. Nested links are invalid: applying a new URL across existing linked text replaces that link's URL rather than nesting anchors. `Space+y` with the cursor inside a Link copies its destination URL to the system clipboard without opening it, confirms success in the footer, and reports clipboard failures without changing the draft. An imported Link with an empty label renders its URL as the styled visible label and can be edited with `Space+l`; Vimkunja does not create new empty-label Links. An imported non-dangerous URL whose scheme is outside M3's allowlist is preserved and rendered as a Link label; its footer says `Unsupported link scheme; preserved`, and the user may replace or remove it but cannot create that scheme anew. Truly unsafe schemes are governed by the global unsafe-HTML safety decision.
18. An untouched opaque subtree survives unrelated edits byte-for-byte, including its tag spelling, attribute order and quoting, whitespace, children, and nesting. Native content before and after it remains editable. A selection may include only the complete opaque atom, never part of it: inline formatting applies to selected native text while skipping the unchanged subtree; deletion or replacement removes a fully included subtree only after confirmation. `x` or `dd` on a focused opaque atom uses the same confirmation. Cancellation leaves the draft and pending input unchanged. Copying includes only the safe visible projection, never hidden URLs, attributes, IDs, or raw Source HTML; pasting that copy creates fully native editable text nodes rather than another opaque subtree. Description-local Undo restores a removed subtree's exact original bytes, position, and nesting, while Redo repeats the confirmed operation without prompting again. Structural changes to a native parent containing an opaque descendant require confirmation and are accepted only when serialize-and-reparse validation retains the subtree byte-for-byte in its intended position. Before each save containing opaque content, one linear-time round-trip validation verifies every retained subtree's bytes, identity, order, nesting, and parent position; deliberately removed subtrees are excluded. Validation is not performed per keystroke, and a failure rejects the save while keeping the draft open. Explicit opaque conversion, unwrapping, and raw-HTML editing are follow-up work. If Source HTML cannot be safely parsed or preserved, Vimkunja creates a Blocked Description rather than risking a destructive write. A malformed Description renders safe best-effort text and reports `Error: Malformed HTML`. It offers two explicit, confirmed recovery actions: **Clear Description**, which creates an empty unsaved draft, and **Recover text**, which creates an editable plain-text draft from the safe projection and enters Insert Mode. Saving either draft intentionally replaces the malformed Source HTML; discarding it retains the source unchanged. Executable or active content—including `script`, event-handler attributes, and dangerous URL schemes such as `javascript:`—also creates a Blocked Description with a safe neutral projection; Vimkunja never automatically sanitizes then saves it.
19. Tables are opaque in V1: Vimkunja renders simple rows as a terminal grid but does not edit their cells, rows, columns, or attributes. For merged, styled, or irregular tables, it renders each source row's cell text separated by `|` rather than inventing a misleading layout. All structure and attributes remain preserved during unrelated edits. A table wider than the Task Detail Pane scrolls horizontally with `zh` and `zl` and exposes a visible overflow indicator. Tables are `j`/`k`-focusable for reading and scrolling; focus says `Table is read-only; preserved`. Formatting skips a selected Table, while deletion or replacement of the complete Table follows the confirmed opaque-subtree flow.
20. Description editing includes Vim-style Visual Mode. `v` begins a selection, which is the basis for applying inline formatting without exposing pseudo-Markdown or HTML. A characterwise selection may span multiple Description blocks and complete opaque atoms; inline formatting applies to every selected native text segment and reports that preserved content was skipped. A selection can never enter or partially include an opaque subtree. Vimkunja never expands a user selection implicitly to word or block boundaries; users select complete words or structures explicitly through motions such as `w`/`b` and future text objects.
21. **Provisional, pending prototype review:** In Description Visual Mode, Vimkunja applies bold, italic, underline, strikethrough, and links through `Space+b`, `Space+i`, `Space+u`, `Space+s`, and `Space+l` respectively. Bold, italic, underline, and strikethrough toggle the selection uniformly: if any selected Native text lacks the mark, apply it throughout; if all selected Native text has it, remove it throughout. Opaque subtrees are skipped and do not participate in this decision. Links retain their separate URL-editing flow. This preserves Vim's direct Visual-Mode motions and operators while avoiding raw markup. `Space+0` removes all inline marks, including Links, while preserving text and all block structure.
22. `V` (Shift+V) begins blockwise Visual Mode, selecting whole logical Description blocks such as paragraphs. `viw` and `vaw` select the inner word and word including surrounding whitespace. Further Visual text objects are deferred beyond V1. `Ctrl+V` rectangular selection is explicitly deferred beyond V1.
23. `Enter` in Insert Mode splits the current paragraph at the cursor into two logical paragraphs, serialized as separate `<p>` blocks. Inside a Block quote, it creates a sibling quoted paragraph at the same depth; on an empty quoted paragraph it exits the quote and creates a following ordinary paragraph. `Shift+Enter` inserts a hard line break (`<br>`) within the current paragraph. A hard break renders as a real terminal row break with a subtle presentation-only `↵` marker at the prior row's end while that paragraph is active; it is hidden when unfocused and falls back to `>` on ASCII-only terminals. Text whitespace immediately beside an imported hard break is retained in the structured document and serialization, including non-breaking spaces. New content follows normal HTML-renderer-visible behavior rather than creating hidden whitespace semantics. Leading, trailing, and consecutive hard breaks are preserved and permitted; each creates its HTML-equivalent visible row, including intentional blank rows. The same rules apply inside headings, list and Checkbox-list entries, and Block quotes; quote prefixes repeat on every resulting row. Code-block newlines remain literal Code text and never become `<br>` nodes. `Backspace` at a paragraph's start merges it with the preceding compatible block; `Delete` at its end merges it with the following compatible block. Within a quote, they merge only adjacent compatible child blocks at the same quote depth and never implicitly pull ordinary text across the quote boundary. A multi-line Plain-Text paste outside a Code block creates paragraphs at line breaks; inside a Code block it preserves source lines. Pasted text that resembles HTML remains literal text; it never creates document markup.
24. In Description Normal Mode, block-format commands act on the current Description block without requiring a selection. Visual Mode is reserved for inline formatting.
25. **Provisional, pending prototype review:** `Space+1`, `Space+2`, and `Space+3` convert the current block to H1, H2, and H3; `Space+0` converts it to a paragraph.
26. `Enter` at the end of a list or Checkbox-list entry creates a new entry of the same kind. `Enter` on an empty entry exits that list and creates a following paragraph.
27. In Description Normal Mode, `x` toggles the current Checkbox-list entry's checked state only. It never changes the enclosing Task record's Done state.
28. **Provisional, pending prototype review:** In Description Normal or Visual Mode, `Space` opens the context-specific Space formatting palette in a secondary footer below the primary footer. When that extra footer would leave fewer than three visible Description rows, it temporarily replaces the primary footer; closing the palette restores the primary footer. At narrow widths, show a compact contextual subset while keeping labels readable. Insert-Mode spaces remain ordinary input. The displayed second-key shortcuts execute the corresponding format action directly, keeping common operations to two keystrokes. It uses the existing Leader timeout and closes on the second key, `Esc`, or timeout. `Space+o` remains the global Projects-Pane toggle, including while editing a Description, so the editor can gain more terminal space. Block conversions use `Space+1/2/3/0` (H1/H2/H3/paragraph), `Space+u/n/x` (unordered/numbered/Checkbox list), and `Space+c/q` (code block/quote). An overlay remains a prototype comparison alternative, not an automatic fallback.
29. The Description editor supports local `u` Undo and `Ctrl+R` Redo for changes to its current, unsaved draft. This is distinct from undoing persisted Task actions. Undo of a confirmed opaque-subtree deletion or replacement restores its exact original bytes, position, and nesting; Redo reapplies it without another confirmation.
30. Saving detects whether the Description changed externally since the editor opened. A conflict rejects the save instead of silently overwriting newer content. The local Draft remains open; the user explicitly chooses to return to it or perform a hard reload of current database content. Vimkunja performs no automatic merge.
31. Reapplying an applicable block-format command to a block of the same type toggles that format off and converts the block to a paragraph. Commands without a meaningful conversion or toggle define their own behavior.
32. In Description Normal Mode, `dd` deletes the current logical Description block, including an atomic horizontal rule. Inside a nonempty Code block, `dd` instead deletes only the current source line; on an empty Code block, it deletes the entire block. Inside a Block quote, `dd` deletes the current child block; deleting its final child removes the quote. In Visual Mode, `d` deletes exactly the selected text or, for a `V` selection, the selected logical blocks.
33. In Description Normal Mode, `o` and `O` insert a new empty paragraph after or before the current logical block and enter Insert Mode. Inside a Code block they instead create a Code line below or above the current source line; inside a Block quote they create an empty quoted child paragraph below or above the current child block at the same quote depth. Both enter Insert Mode.
34. In Description Normal Mode, `i`, `a`, `I`, and `A` enter Insert Mode at the cursor, after the cursor, and at the start or end of the current logical line respectively. For normal text, the logical line is the complete paragraph or List entry; within a Code block, it is the current source line. A hard break remains inside its paragraph: `j`/`k` do not stop at it, while `gj`/`gk` traverse its resulting visual rows. Left/right motions cross it; `Backspace` immediately after it and `Delete` immediately before it remove it and join its adjacent text. `0`, `^` or `_`, and `$` move to the start, first nonblank position, and end of that line without entering Insert Mode. `w` and `b` traverse words across Inline formatting and Links, and stop at block boundaries. Disclosed editable delimiters behave as ordinary Vim characters, including in counted character motions such as `5l`. Protected presentation markers are skipped without consuming character or word counts. Every complete Opaque subtree is one word-motion unit for `w`, `b`, and `e`, regardless of its projection's internal words. `e` and `ge` move to word ends forward and backward. `gg` and `G` jump to the start and end of the entire structured Description document. `Ctrl+D` and `Ctrl+U` move the cursor by approximately one visible Task Detail Pane height. Visual Mode extends the selection with these motions; `o` swaps its active end and `Esc` cancels it.
35. `{` and `}` move backward and forward by paragraph-motion units; counts apply. Normal-mode `ö` and `ä` are German-keyboard aliases for `{` and `}`. Every navigable Description block is one paragraph-motion unit, including each heading, List or Checkbox-list entry, quote, rule, table, and complete Code block. A Code block remains one unit regardless of its internal source lines or blank lines; `j` and `k` navigate those Code lines locally. A quote likewise remains one unit for `{`/`}`, while `j` and `k` navigate its child blocks locally.
36. Code-block editing uses ordinary Description Normal and Insert modes rather than a separate mode. `Enter` in a Code block inserts a literal source line, and pasted text preserves all line breaks and whitespace. `Esc` only returns to Normal Mode.

## First native editing set

V1 natively renders and edits:

- paragraphs and headings (`h1`–`h3`)
- bold, italic, underline, and strikethrough text
- code blocks and block quotes
- unordered and ordered lists
- Checkbox lists
- links
- horizontal rules

Tables are initially opaque, with a readable terminal-table projection. Images are likewise readable but opaque: render `[Image: alt]`, falling back to `[Image: title]` or `[Image]`; M3 neither renders pixels nor uploads, edits, or replaces image metadata. Generic VOA Task Attachments are separate Task-level records rather than Description markup; only image attachments may also appear as `<img>` nodes. Existing VOA user mentions are readable opaque inline atoms rendered as `@label`, falling back to `@id`, with no M3 creation or internal editing flow. Imported embedded media (`iframe`, `video`, `audio`, `embed`, or `object`) is one atomic opaque `[Embedded media]` block. M3 does not introduce a generic attachment block in Descriptions; later Task Detail Pane attachment browsing/management remains open for separate evaluation. Each outermost opaque structure follows the global atomic preservation rules: ordinary edits preserve its complete original HTML byte-for-byte; focus and copy reveal only its safe projection, never hidden source URLs, IDs, attributes, or raw markup; formatting skips it; and complete deletion or replacement requires confirmation. Copying its safe projection and pasting creates native editable text, not a duplicate opaque structure. An unknown but safely parseable element with text content recursively contributes that text to the outermost opaque subtree's safe projection using known child semantics where possible; a structurally empty unknown element renders `[Unsupported content]`. Future Tiptap extensions remain opaque until their rendering and preservation behavior is specified.

Safe unknown attributes do not by themselves make a Native node opaque. Native nodes retain every safe unknown attribute by name and decoded value, while serialization may normalize attribute order, quoting, and equivalent entity spelling. A structural conversion carries safe unknown attributes onto the replacement element; if an attribute cannot be carried safely, the conversion is rejected rather than silently dropping it. Duplicate attribute names on a Native element, compared case-insensitively, make the entire Description Blocked because choosing one parser-recovered value would silently discard another. Duplicate attributes inside an Opaque subtree remain part of its byte-preserved source and are not interpreted independently. An imported `style` attribute prevents its element from being Native: the outermost styled structure becomes an Opaque subtree whose original HTML is preserved exactly, while Vimkunja renders a safe projection and never applies the CSS. This avoids a security-sensitive CSS parser without discarding valid VOA formatting. Explicitly dangerous active content detected in or around that structure still makes the entire Description Blocked under the global safety rule. An HTML comment is likewise one Opaque atom, rendered only as `[HTML comment]` without disclosing its contents. It is never preserved invisibly: users can focus it and use the ordinary confirmed Opaque deletion, replacement, Undo, and Redo flows.

## Native serialization contract

Native serialization preserves document meaning rather than source spelling. It may normalize tag form, attribute order and quoting, equivalent entity spelling, and whitespace that does not represent Description content. It must preserve meaningful text whitespace, Code-block contents, hard breaks, empty editable blocks, list structure, mark semantics and nesting depth, Link destinations and meaningful attributes, and Checkbox state and identity. It never substitutes visually similar but structurally different content, such as replacing `<br>` with a text newline. Contiguous top-level text and inline nodes in an otherwise valid imported fragment become one Native paragraph and serialize inside `<p>...</p>`; this is accepted structural normalization rather than malformed-HTML recovery. An empty Source HTML string remains an empty Description until the user creates content. Document-level markup such as `<!doctype>`, `<html>`, `<head>`, or `<body>` is invalid in a Description fragment and makes the Description Blocked; Vimkunja does not silently strip wrappers or rely on parser relocation.

Native text is serialized from decoded characters using one canonical HTML-escaping policy. Required escapes such as `&amp;` and `&lt;` appear only in persisted Source HTML; the Terminal projection continues to show decoded user-facing text. Unicode remains Unicode unless valid HTML requires escaping. Outside Code blocks and whitespace immediately beside imported hard breaks, runs of ordinary HTML-collapsible spaces, tabs, and source newlines in Native prose normalize to one visible separating space, and invisible collapsible whitespace at block boundaries may be removed. Non-breaking spaces and other non-collapsing Unicode whitespace remain distinct. Code-block text retains its exact decoded characters, including indentation, tabs, blank lines, and a final newline, even though characters that require HTML escaping are escaped in Source HTML.

Semantic round-trip tests aim to check every listed aspect of Native meaning: document structure, text, marks and their nesting, block boundaries, list and Checkbox state and identity, Links and their meaningful attributes, and exact decoded Code-block content. A check may be omitted when an exception makes it inapplicable. Tests ignore representation-only differences permitted above. Opaque-subtree checks verify exact original bytes after unrelated edits, including tag spelling, attributes, whitespace, children, and nesting, as well as retained identity, order, and parent position. Blocked Descriptions have no automatic-save or round-trip claim, and deliberately removed content is excluded from preservation checks.

Empty editable block positions remain structural content. Empty paragraphs serialize as `<p></p>`; empty headings, Code blocks, Block quotes, and individual list entries remain representable and persist. Deleting a list's final entry removes the now-entry-less outer list or Checkbox-list container. Empty inline-mark wrappers are removed. An imported empty-label Link remains preserved under the Link rules, but Vimkunja does not create one. Vimkunja does not insert `<br>` merely to make an empty block visible in the TUI.

Canonical Native mark output is standards-aligned rather than based only on visual similarity. Newly applied bold, italic, underline, and strikethrough use `<strong>`, `<em>`, `<u>`, and `<s>`. Imported `<b>`/`<strong>` and `<i>`/`<em>` variants retain their distinct HTML semantics, including repeated `<strong>` or `<em>` depth. Only obsolete `<strike>` is normalized to `<s>`.

## Compatibility corpus and test harness

Native rich-text implementation must be guided by a representative compatibility corpus, not only by isolated happy-path examples. The corpus is created through greenfield example brainstorming and the ticket's grilling decisions, with fixtures for valid Vikunja/Tiptap HTML, unsupported and opaque structures, and malformed or unsafe input.

The initial fixture categories include:

- nested ordered, unordered, and Checkbox lists
- headings and paragraphs combined with inline marks, links, and hard breaks
- adjacent or overlapping marks and formatted link text
- Unicode, entities, significant whitespace, empty blocks, and HTML-looking code text
- quotes containing lists or formatted content, code blocks, and horizontal rules
- tables mixed with editable content
- unknown or opaque subtrees, unusual attributes, and historical Checkbox entries without IDs
- malformed, partially parseable, unsafe, and structurally empty content

The corpus consists of many focused Source HTML snippets rather than one comprehensive example. Each settled rich-text decision maps through a traceability matrix to at least one focused fixture, and a smaller set of compound fixtures covers risky interactions between features. The initial compound set includes quotes containing lists or Code blocks, formatting inside Links, Opaque content between editable text, and Tables mixed with editable content; add cases if the inventory walkthrough reveals further risks. Fixtures are grouped by expected classification—Native, mixed Native/Opaque, or Blocked—and use stable descriptive names. The corpus combines exact VOA-generated output, synthetic edge cases that VOA cannot conveniently create, and minimized regression inputs from later defects. Every fixture records its provenance; VOA-generated fixtures record the Vikunja version when known. Sensitive content may be anonymized only while preserving the relevant HTML structure and attributes.

Walk through every agreed decision and known rich-text element, from basic blocks to advanced behavior, and create happy-path and relevant corner-case examples for each. Track coverage in the traceability matrix. There is no rigid fixture-count definition of done; a practical completion check is that every decision/element has relevant examples and the matrix has no known uncovered entries after review. Across the suite, fixtures collectively provide sufficient regression coverage for four goals: terminal projection, Native/Opaque/Blocked classification, save/round-trip behavior, and representative editing behavior. No individual fixture must cover every goal; each covers the goals relevant to it. Each fixture records its original Source HTML, expected classification, Terminal projection, canonical Native serialization or exact Opaque bytes, representative edit and expected result where editing is available, warnings/confirmations/save rejection, and tested semantic invariants. A Blocked fixture may have no ordinary edit, but must assert rejection and its explicit recovery behavior. Expected projections and serialized outputs are manually reviewed contract artifacts, never silently regenerated from the implementation under test. A maintenance command may propose golden-file updates, but accepting them requires an explicit diff and an explanation of the changed contract decision; semantic comparisons may parse expected HTML but must not derive expectations from the serializer being tested. The test harness must verify that parsing and rendering do not panic or expose raw markup, supported content round-trips to equivalent Vikunja-compatible HTML semantics, opaque structures survive unrelated edits, unsafe content becomes read-only instead of being destructively rewritten, and Description edits never change the enclosing Task's Done state. It should provide fixture-based regression tests and semantic round-trip tests. Property tests should verify that valid Native content parses and serializes back to equivalent meaning, and that parsing/rendering never panics or exposes raw markup. A small, bounded fuzz run in regular CI should exercise arbitrary, malformed, partially parseable, and unsafe inputs at parser/serializer boundaries. No longer scheduled fuzz runs are required; discovered defects should become deterministic regression cases. Prioritize a comprehensive deterministic suite for known issues and contract cases.

The corpus, traceability matrix, and expected behaviors are specification deliverables and must be established before native editing implementation begins.

## Projection principle

> Friendly projection by default, source disclosure near the cursor.

The current logical block reveals its editable source syntax in Normal and Insert modes; cursor motions operate over the disclosed source characters. Away from the cursor, the user-friendly interpretation is rendered. This applies uniformly to headings, inline marks, and horizontal rules. A Code block discloses its entire canonical triple-backtick enclosure while the cursor is anywhere inside it, while retaining the background across the whole block. Its fences are a deliberate exception: they are protected structural markers, not cursor targets or editable content. Markdown-like delimiters are editor syntax only; persistence remains semantic Vikunja-compatible HTML.

Typing three or four consecutive backticks in an otherwise empty paragraph creates the same structured Code block, consumes the trigger, and places the cursor on an empty Code line between canonical triple-backtick fences. This input convenience never persists a fourth backtick and never exposes HTML.

Lists use indentation and ordinary markers; Checkbox entries use `☐`/`☑`. Checkbox toggles never change the enclosing Task Done state. Historical entries without IDs remain editable and receive a lowercase UUID v4 on the next successful Description save. Quotes use their non-editable presentation prefixes rather than disclosed pseudo-Markdown syntax. Imported empty quotes render as one empty editable quoted line and are preserved on save; `Space+q` on an empty paragraph creates one. The Vimkunja Markdown-like markup dialect must be documented in Help and durable user documentation, and taught in a dedicated Vimkunja markup-tutorial section.

## Editor syntax and atomic presentation

These rules govern editor syntax, not Source HTML:

- `***text***` applies one bold and one italic layer and serializes as `<strong><em>text</em></strong>`; it does not encode repeated emphasis.
- Imported repeated semantic emphasis discloses nested delimiter pairs with visible protected separators between layers. Separators distinguish repeated layers from combined bold/italic, are not cursor targets, and are never persisted.
- A backslash escapes the next syntax character: backslash, `*`, `_`, `~`, backtick, `#`, `-`, `+`, `.`, or square bracket. Before other characters or at a block's end it remains literal. Escapes are editor syntax only; Source HTML stores the resulting literal characters. Existing unmatched, mismatched, or overlapping delimiter sequences remain literal.
- At a logical block's start, directly typed `# `, `## `, or `### ` creates a heading; `- `, `+ `, `* `, or `1. ` creates a list entry. These triggers require a following space. A dash-only line of at least three dashes creates a rule; three or four backticks in an otherwise empty paragraph creates a Code block. Escaping the first marker prevents conversion.
- Pasting never triggers structural conversion. Pasting `# Shopping` followed by `- Milk` creates two ordinary paragraphs containing those literal markers, not a heading and list.
- Protected markers (quote prefixes, Code fences, emphasis-layer separators) are skipped by motions and may be crossed by selections but are never copied, deleted, or formatted as text. Editable delimiters remain ordinary cursor targets.
- Opaque subtrees must visibly form atomic units, including when their safe projection contains multiple words or rows. Use enclosing brackets/outline plus subtle highlighting, with a non-color boundary cue and a marked multiline extent. Bracket style and highlighting color are configurable. Exact styling awaits prototype review; raw attributes remain hidden.

## Provisional layout and prototype validation

The following decisions require practical validation, not merely specification agreement:

- Anchor the cursor to its document character or insertion boundary, not terminal coordinates. Disclosure recalculates its screen position without changing its editing target.
- Reflow the whole current logical block when disclosing syntax. Other blocks retain their own layout but may shift vertically. Code blocks retain whole-block fence disclosure and never soft-wrap.
- Preserve the cursor's screen row where possible by compensating vertical scroll; clamp at document boundaries and keep the cursor visible. Focus transitions do not reset Code/Table horizontal scroll.
- Wrap ordinary text and editable delimiters without hiding characters; keep protected separators attached to neighboring delimiters. `gj`/`gk` navigate wrapped visual rows. Mark soft-wrap continuation rows with a small non-editable arrow, distinct from the hard-break marker. Code and Tables retain horizontal scrolling.
- If fixed prefixes leave no room for one content character, show `Pane too narrow` while preserving the draft and document cursor position.
- Validate wide and narrow layouts using formatted paragraphs, nested lists/quotes, and Opaque subtrees. Include practical examples of cursor anchoring, disclosure reflow, scrolling, wrap arrows, and atomic boundaries before accepting readability.
- Validate the Space formatting palette's secondary footer and fewer-than-three-content-rows replacement threshold. Compare an overlay as an alternative. Normal bindings remain `Space+1/2/3/0`, `Space+u/n/x`, and `Space+c/q`; Visual bindings remain `Space+b/i/u/s/l` and `Space+0`. Mode-specific differences need comfort/conflict review.
- Validate uniform mark toggling on mixed selections; semantic policy is agreed, while interaction comfort remains subject to prototype review.

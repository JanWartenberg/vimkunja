## Purpose

Vikunja stores rich-text Task Descriptions as HTML. Vimkunja must provide a keyboard-first terminal editing experience without exposing HTML source for normal editing, while continuing to store Vikunja-compatible HTML and without changing the database schema.

## Terms

- **Source HTML:** HTML read from and written to Vikunja's existing `tasks.description` field.
- **Description document:** Vimkunja's structured interpretation of Source HTML for rendering and editing.
- **Terminal projection:** The keyboard-navigable, terminal-appropriate rendering of a Description document. It need not be visually identical to the web application.
- **Description block:** A logical block in a Description document, such as a paragraph, heading, list item, code block, quote, or table.
- **Checkbox list:** A checklist embedded in a Description, represented by Vikunja/Tiptap `data-type="taskList"` HTML. This is distinct from Vimkunja's Tasks Pane and its Task records.
- **Native node:** A safely parsed Description structure that Vimkunja understands and can edit through its Terminal projection.
- **Opaque subtree:** The outermost safely parsed Description structure that Vimkunja cannot edit internally. It is one atomic unit whose original HTML is preserved during unrelated edits.
- **Blocked Description:** A Description whose source boundaries cannot be preserved reliably enough to isolate the problem, so editing/saving the whole Description stays disabled until explicit recovery. A reliably bounded problem is protected locally as Opaque, or only its unsafe operation is rejected; unknown or active content alone does not imply whole-Description blocking.

## Captured Checkbox compatibility — 2026-10-11

The actual upstream editor component serializes task items with a checkbox control (`label` containing `input` and an empty `span`) followed by a content `div`. These known wrappers are Native implementation scaffolding: text and nested lists remain editable, the control is not a separate terminal editing target, and `input.checked` follows `li.data-checked`. Ordinary saves retain the wrappers; explicit list splits/conversions may emit the equally understood direct paragraph/list representation. Only the concrete safe shape is recognized. Unknown/unsafe control attributes stay Opaque locally; an attribute-free known content wrapper remains Native even when the adjacent control is protected. Generic HTML forms/divs are not made Native by this exception.

## Agreed principles

1. Source HTML remains the persistence format. Vimkunja does not store an alternative format or change Vikunja's schema.
2. Normal editing must not require the user to read or edit HTML source.
3. M2's completed reader-only phase uses a deliberately lossy HTML-to-plain-text projection for display. It never writes Source HTML. Native rendering, editing, and saving use a structured document model rather than lossy conversion.
4. Existing opaque subtrees must not be changed by an unrelated edit. The outermost opaque ancestor is one atomic subtree; its descendants may contribute to its safe projection but are not independently focused, selected, edited, or validated. More generally, Vimkunja preserves every safely parseable existing Source HTML structure and attribute unless an explicit, accepted rule permits a semantic rewrite; surprising data loss is not an acceptable normalization.
5. Unsupported terminal presentation degrades to readable content; it must not display literal markup merely because it is unsupported. Unknown parseable HTML renders its text contents recursively without special formatting; structurally empty unsupported content displays a neutral unsupported-content hint.
6. Native terminal formatting is semantic where possible. Terminal capabilities may affect visual fallback, but not the document's HTML meaning.
7. Paragraphs and other Description blocks are parsed from Source HTML even when that HTML is stored as one long string. The Terminal projection separates logical blocks for navigation; it does not navigate HTML source text.
8. Saving uses hybrid serialization: Native nodes become compact, canonical HTML under the semantic rules below, while every retained Opaque subtree preserves its original Source HTML byte-for-byte. Presentation-only indentation and line breaks are never added between Native elements.
9. In a Description, `j` and `k` jump between navigable logical blocks: paragraphs, headings, and individual list or Checkbox-list entries. `gj` and `gk` move between visual terminal rows created by soft-wrapping a navigable text block.
10. Checkbox lists are part of the first native editable subset. Vimkunja can add and remove their entries and toggle their checked state. This changes only the Description document's `data-checked` state, never the enclosing Task record's Done status. On every successful Description save, Vimkunja assigns a unique lowercase UUID v4 `data-task-id` to every Checkbox entry that lacks one. Existing unique IDs, including non-UUID values, are not regenerated, and subsequent saves retain each generated ID. On successful save, missing and duplicate Checkbox IDs are repaired automatically, without confirmation: preserve the first occurrence of each existing nonempty Native ID in document order and assign fresh non-colliding lowercase UUID v4 values only to missing IDs and later duplicates. Never clear or regenerate all IDs in an affected list. Preserve text, order, nesting, checked states, unrelated attributes and retained Opaque bytes; ID problems alone do not make an otherwise understood list Opaque or read-only. Reserve existing IDs before generating replacements. Build repair candidates without partial writes; an external conflict or failed save leaves the original persisted Description and the local draft unchanged. Confirmation is required only for an operation that would lose actual content or other meaningful metadata, not for pure ID maintenance. Existing preservation exceptions remain narrow; this does not authorize automatic conversion of unknown Opaque structures. Duplicating an entry through Vimkunja always creates a fresh ID rather than copying the original entry's ID.
11. Headings `h1` through `h3` are part of the first native editable subset.
12. Bold, italic, underline, and strikethrough are part of the first native editable subset. Their terminal projections may use capability-dependent visual fallbacks without changing their HTML meaning. HTML's semantic distinctions remain part of the Native model even when the terminal style is identical: imported `<b>` remains distinct from `<strong>`, and imported `<i>` remains distinct from `<em>`. New Vimkunja bold and italic formatting serializes as `<strong>` and `<em>`; obsolete imported `<strike>` normalizes to `<s>`. Nested `<strong>` and `<em>` depth is semantically significant and must not be flattened.
13. Ordered and unordered lists are part of the first native editable subset. Nested lists are rendered and preserved in V1. Their existing text and Checkbox-list state remain editable. V1 now includes explicit list-depth increase/decrease through the block-selection structure palette. For one selected entry, increasing depth makes it a child of its previous sibling. Without a previous sibling, reject the operation without mutation and show a clear hint; do not invent an empty parent, orphan nesting, or CSS-only indentation. The user explicitly accepted this conventional structural rule despite its limitation, with no useful deviation identified. Outdenting an entry moves its descendants with it, preserving the subtree. Child entries remain independently selectable for indent/outdent; selecting a parent does not require selecting its children separately to preserve them during the parent's outdent. The accepted movement, selection, boundary, and numbering rules are recorded under V1 structural decisions below. Their focused fixture expectations are recorded in the corpus traceability matrix; Native execution and technical validation remain outstanding. Other structural nesting edits remain deferred.
14. Code blocks are part of the first native editable subset. They use a theme-configurable background across the entire block plus a thin presentation-only `│` prefix as a non-color fallback. Multi-line Code blocks preserve every source character, including indentation, tabs, blank lines, and a final trailing newline, without soft wrapping or serialization normalization; overwide code scrolls horizontally with `zh`/`zl` and shows a one-row, non-editable scrollbar inside the block only while content overflows.
15. Block quotes are part of the first native editable subset. A Block quote is HTML `<blockquote>`, an extended quotation distinct from inline `<q>`. Its first visual row has the presentation-only prefix `│  ` and wrapped continuation rows have `│↪ `; ASCII fallbacks are `|  ` and `|> `. Nested quotes add one prefix per depth. Prefixes are never cursor targets or editable in either mode, and no quote-specific background or color is required. A quote contains any native editable Description blocks, including nested quotes and Code blocks. Parseable existing `cite` and VOA `data-comment-id` attributes are preservation-only: Vimkunja carries them through safe unrelated edits but offers no M3 input or editing UI or Task-Description reply semantics.
16. Horizontal rules are part of the first native editable subset. A rule is an atomic, selectable Description block. In Normal Mode, `dd` deletes the whole rule block. `x` deletes one displayed dash at a time; once fewer than three dashes remain, the content becomes ordinary paragraph text. Visual selection editing may be added in a future iteration.
17. Links are part of the first native editable subset. Their terminal editing flow operates on visible link text and a separate URL, never on raw `<a>` markup. Links render as their visible label, with underline/color when supported and without an inline URL. With the cursor inside a link, the status/footer shows `Link → URL · typing extends link · Space+l edit`; immediately at a link edge it instead says `Link edge → URL · typing is outside link`. `Space+l` opens the URL prompt. `Space+l` in characterwise Visual Mode (`v`) applies a prompted URL to the selected text; in Description Normal Mode with a cursor inside an existing link, it prompts with the existing URL. Link text remains ordinary editable Description text. Text inserted inside an existing link remains linked; text inserted exactly before or after it remains ordinary text, so extending a link requires explicitly selecting the desired text and applying `Space+l`. An empty URL removes the link. M3 accepts only VOA's absolute `://` URL schemes—`http`, `https`, `ftp`, `git`, `obsidian`, `notion`, and `message`—and rejects relative, schemeless, and other URLs while keeping the prompt open with a clear error. The allowed-scheme policy must be centralized and deliberately extensible for a future approved tool/protocol extension, rather than embedded across editor flows. M3's allowlist is fixed: a future extension must explicitly approve a new protocol through its own configuration or extension contract; unknown imported schemes do not become newly creatable merely by appearing in existing data. Every serialized Native Link uses Vikunja's `target="_blank"` behavior, including an imported Link that originally omitted `target` or used another target. New or edited Links emit canonical `href` and `target="_blank"`; safe, meaningful imported attributes such as `title`, `rel`, and compatible data attributes are preserved semantically, without preserving attribute order or quoting. Vimkunja does not invent `rel="noopener"` when it is absent. Unsafe or ambiguous Link attributes protect the smallest reliably isolatable Link/subtree as Opaque rather than being silently dropped or automatically blocking its Native neighbors. Active destinations are not opened. Link labels may freely combine bold, italic, underline, strikethrough, and hard breaks; serialize their formatting inside the `<a>` element in canonical form. Nested links are invalid: applying a new URL across existing linked text replaces that link's URL rather than nesting anchors. `Space+Y` with the cursor inside a Link copies its destination URL to the system clipboard without opening it, confirms success in the footer, and reports clipboard failures without changing the draft. An imported Link with an empty label renders its URL as the styled visible label. Focus and URL-only edits keep the stored label empty. The first actual label edit materializes the current URL fallback once, applies the edit, and keeps href unchanged. Explicit unlink retains that visible fallback as plain text; explicit content deletion removes it. Vimkunja does not create new empty-label Links. An imported non-dangerous URL whose scheme is outside M3's allowlist is preserved and rendered as a Link label; its footer says `Unsupported link scheme; preserved`, and the user may replace or remove it but cannot create that scheme anew. Truly unsafe schemes are governed by the global unsafe-HTML safety decision.
18. An untouched opaque subtree survives unrelated edits byte-for-byte, including its tag spelling, attribute order and quoting, whitespace, children, and nesting. Native content before and after it remains editable. A selection may include only the complete opaque atom, never part of it: inline formatting applies to selected native text while skipping the unchanged subtree; deletion or replacement removes a fully included subtree only after confirmation. `x` on a focused opaque atom uses the same confirmation. `dd` and blockwise `V d` delete the current/selected complete logical blocks, including their Native text and inline Opaque descendants, even when the cursor is on an inline atom. Such deletion requires one confirmation for the whole operation; cancellation leaves everything unchanged and Undo restores the whole deleted content, including exact Opaque bytes and position. For a standalone Opaque block, `dd` deletes that block after confirmation. A wrapped screen row is not a logical block. Cancellation leaves the draft and pending input unchanged. Copying includes only the safe visible projection, never hidden URLs, attributes, IDs, or raw Source HTML; pasting that copy creates fully native editable text nodes rather than another opaque subtree. Description-local Undo restores a removed subtree's exact original bytes, position, and nesting, while Redo repeats the confirmed operation without prompting again. Structural changes to a native parent containing an opaque descendant require confirmation and are accepted only when serialize-and-reparse validation retains the subtree byte-for-byte in its intended position. Before each save containing opaque content, one linear-time round-trip validation verifies every retained subtree's bytes, identity, order, nesting, and parent position; deliberately removed subtrees are excluded. Validation is not performed per keystroke, and a failure rejects the save while keeping the draft open. Explicit opaque conversion, unwrapping, and raw-HTML editing are follow-up work. If Source HTML cannot be safely parsed or preserved, Vimkunja creates a Blocked Description rather than risking a destructive write. A malformed Description renders safe best-effort text and reports `Error: Malformed HTML`. It offers two explicit, confirmed recovery actions: **Clear Description**, which creates an empty unsaved draft, and **Recover text**, which creates an editable plain-text draft from the safe projection and enters Insert Mode. Saving either draft intentionally replaces the malformed Source HTML; discarding it retains the source unchanged. Executable or active content—including `script`, event-handler attributes, and dangerous URL schemes such as `javascript:`—is never executed or opened by the TUI. A reliably bounded subtree is preserved as Opaque with a safe projection while its Native neighbors remain editable and savable. Protect a larger region, up to the whole Description, only when its source boundaries cannot be preserved reliably. Never automatically sanitize then save. Reject only an unsafe structural operation when other edits remain preservable; any failed save-time preservation check rejects the save and retains the draft.
19. Tables are opaque in V1: Vimkunja renders simple rows as a terminal grid but does not edit their cells, rows, columns, or attributes. For merged, styled, or irregular tables, it renders each source row's cell text separated by `|` rather than inventing a misleading layout. All structure and attributes remain preserved during unrelated edits. A table wider than the Task Detail Pane scrolls horizontally with `zh` and `zl` and exposes a visible overflow indicator. Tables are `j`/`k`-focusable for reading and scrolling; focus says `Table is read-only; preserved`. Formatting skips a selected Table, while deletion or replacement of the complete Table follows the confirmed opaque-subtree flow.
20. Description editing includes Vim-style Visual Mode. `v` begins a selection, which is the basis for applying inline formatting without exposing pseudo-Markdown or HTML. A characterwise selection may span multiple Description blocks and complete opaque atoms; inline formatting applies to every selected native text segment and reports that preserved content was skipped. A selection can never enter or partially include an opaque subtree. Vimkunja never expands a user selection implicitly to word or block boundaries; users select complete words or structures explicitly through motions such as `w`/`b` and the accepted `viw`/`vaw` text objects.
21. **Accepted design; practical validation outstanding:** In Description characterwise Visual Mode (`v`), Vimkunja applies bold, italic, underline, strikethrough, and links through `Space+b`, `Space+i`, `Space+u`, `Space+s`, and `Space+l` respectively. Bold, italic, underline, and strikethrough toggle the selection uniformly: if any selected Native text lacks the mark, apply it throughout; if all selected Native text has it, remove it throughout. Explicit Bold-off removes every bold-family layer (`b` and `strong`) from the selected Native text, including double and triple `strong`, rather than leaving a visually bold remainder. Unrelated edits still preserve imported variants and semantic depth; other marks remain unchanged. Italic/Underline/Strike-off likewise removes all selected layers of its own family (accepted E01); other marks remain unchanged. Formatting keeps the document-anchored selection until Esc. Opaque subtrees are skipped and do not participate in this decision. Links retain their separate URL-editing flow. This preserves Vim's direct Visual-Mode motions and operators while avoiding raw markup. `Space+0` removes all inline marks, including Links, while preserving text and all block structure.
22. `V` (Shift+V) begins blockwise Visual Mode, with the footer label `VISUAL BLOCKS`, selecting whole logical Description blocks such as paragraphs. Ordinary Visual motions extend the selection and `d` deletes it; structure shortcuts do not take over until `Space` opens the context-specific structure palette. Its accepted V1 pairs are `q/w` (remove/add one quote layer), `k/l` (decrease/increase list depth), and `x/c` (unindent/indent Code). Thus `V`, motions, `Space`, then an action is a selection workflow, not a fixed three-key command. Actions apply only in the relevant structural context; validate mixed structural selections before mutation and reject an incompatible operation atomically. Code indentation width is configurable, defaults to four spaces, and accepts two or four spaces per explicit step. The accepted C03 Tab preservation, explicit conversion, and literal-insertion rules are recorded below; Tab/indent behavior and clamped Code-line selection are accepted below. Configuration uses the existing user TOML under tui; exact Description-specific keys remain open. Indentation must not otherwise normalize Code. This is explicit user editing of Code whitespace, not serialization normalization. These blockwise pairs do not replace characterwise `v`'s inline palette: in `v`, `Space+l` remains Link editing; in `V`, it increases list depth. Exact structure-operation semantics and practical palette presentation still require validation. `viw` and `vaw` select useful semantic text without automatically including its delimiters. At a delimiter select the nearest inner useful word; an empty expression produces a hint. `h/l` can still reach each ASCII delimiter. Cursor movement/deletion treats a visible grapheme cluster as one character, including combining accents and ZWJ emoji. Further Visual text objects are deferred beyond V1. `Ctrl+V` rectangular selection is explicitly deferred beyond V1.
23. `Enter` in Insert Mode splits the current paragraph at the cursor into two logical paragraphs, serialized as separate `<p>` blocks. Inside a Block quote, it creates a sibling quoted paragraph at the same depth; on an empty quoted paragraph it exits the quote and creates a following ordinary paragraph. `Shift+Enter` inserts a hard line break (`<br>`) within the current paragraph. A hard break renders as a real terminal row break with a subtle presentation-only `↵` marker at the prior row's end while that paragraph is active; it is hidden when unfocused and falls back to `>` on ASCII-only terminals. Text whitespace immediately beside an imported hard break is retained in the structured document and serialization, including non-breaking spaces. New content follows normal HTML-renderer-visible behavior rather than creating hidden whitespace semantics. Leading, trailing, and consecutive hard breaks are preserved and permitted; each creates its HTML-equivalent visible row, including intentional blank rows. The same rules apply inside headings, list and Checkbox-list entries, and Block quotes; quote prefixes repeat on every resulting row. Code-block newlines remain literal Code text and never become `<br>` nodes. `Backspace` at a paragraph's start merges it with the preceding compatible block; `Delete` at its end merges it with the following compatible block. Within a quote, they merge only adjacent compatible child blocks at the same quote depth and never implicitly pull ordinary text across the quote boundary. A multi-line Plain-Text paste outside a Code block creates paragraphs at line breaks; inside a Code block it preserves source lines. Pasted text that resembles HTML remains literal text; it never creates document markup.
24. In Description Normal Mode, block-format commands act on the current Description block without requiring a selection. Characterwise Visual Mode supplies inline formatting; Blockwise Visual Mode supplies the separate structural palette.
25. **Accepted design; practical validation outstanding:** `Space+1`, `Space+2`, and `Space+3` convert the current block to H1, H2, and H3; `Space+0` converts it to a paragraph.
26. `Enter` at the end of a list or Checkbox-list entry creates a new entry of the same kind. `Enter` on an empty entry exits that list and creates a following paragraph.
27. In Description Normal Mode, `x` toggles the current Checkbox-list entry's checked state only. It never changes the enclosing Task record's Done state.
28. **Accepted design; practical validation outstanding:** In Description Normal or Visual Mode, `Space` opens the context-specific Space formatting palette in a secondary footer below the primary footer. When that extra footer would leave fewer than three visible Description rows, it temporarily replaces the primary footer; closing the palette restores the primary footer. At narrow widths, show a compact contextual subset while keeping labels readable. Insert-Mode spaces remain ordinary input. The displayed second-key shortcuts execute the corresponding format action directly, keeping common operations to two keystrokes. It uses the existing Leader timeout and closes on the second key, `Esc`, or timeout. `Space+o` remains the global Projects-Pane toggle, including while editing a Description, so the editor can gain more terminal space. Normal-Mode block conversions use `Space+1/2/3/0` (H1/H2/H3/paragraph), `Space+u/n/x` (unordered/numbered/Checkbox list), and `Space+c/q` (code block/quote). Characterwise v uses the inline palette; blockwise V uses the separate structural pairs in principle 22. An overlay remains a prototype comparison alternative, not an automatic fallback.
29. The Description editor supports local `u` Undo and `Ctrl+R` Redo for changes to its current, unsaved draft. This is distinct from undoing persisted Task actions. Undo of a confirmed opaque-subtree deletion or replacement restores its exact original bytes, position, and nesting; Redo reapplies it without another confirmation.
30. Saving detects whether the Description changed externally since the editor opened. A conflict rejects the save instead of silently overwriting newer content. The local Draft remains open; the user explicitly chooses to return to it or perform a hard reload of current database content. Vimkunja performs no automatic merge.
31. Reapplying an applicable block-format command to a block of the same type toggles that format off and converts the block to a paragraph. Commands without a meaningful conversion or toggle define their own behavior. `Space+q` wraps an unquoted current block in a Block quote; when already quoted, it removes the applicable surrounding quote layer while retaining its child content, rather than adding a deeper layer. Quote-depth increase and decrease use the agreed blockwise structure palette: `V`, selection motions, `Space+q/w` remove/add one applicable quote layer. Selected sibling blocks share one added quote layer; removing a layer affects only the selected children, splitting the existing container as necessary without pulling unselected neighbors along. An incompatible quote-reduction selection rejects atomically. Metadata loss on removal requires the explicit confirmation described under V1 structural decisions; attributes must not be silently lost or unique identities duplicated. Known shared source references may remain on both retained Quote fragments as specified below. `V >/<` was rejected in favor of the Space-led pairs. Imported nested quotes remain preserved.
32. In Description Normal Mode, `dd` deletes the current logical Description block, including an atomic horizontal rule. Inside a nonempty Code block, `dd` instead deletes only the current source line; deleting its final nonempty line leaves an empty Code block (C05). A subsequent `dd` on the empty Code block deletes the block. Inside a Block quote, `dd` deletes the current child block; deleting its final child removes the quote. In Visual Mode, `d` deletes exactly the selected text or, for a `V` selection, the selected logical blocks.
33. In Description Normal Mode, `o` and `O` insert a new empty paragraph after or before the current logical block and enter Insert Mode. Inside a Code block they instead create a Code line below or above the current source line; inside a Block quote they create an empty quoted child paragraph below or above the current child block at the same quote depth. Both enter Insert Mode.
34. In Description Normal Mode, `i`, `a`, `I`, and `A` enter Insert Mode at the cursor, after the cursor, and at the start or end of the current logical line respectively. For normal text, the logical line is the complete paragraph or List entry; within a Code block, it is the current source line. A hard break remains inside its paragraph: `j`/`k` do not stop at it, while `gj`/`gk` traverse its resulting visual rows. Left/right motions cross it; `Backspace` immediately after it and `Delete` immediately before it remove it and join its adjacent text. `0`, `^` or `_`, and `$` move to the start, first nonblank position, and end of that line without entering Insert Mode. `w` and `b` traverse words across Inline formatting and Links, and stop at block boundaries. Disclosed editable delimiters behave as ordinary Vim characters, including in counted character motions such as `5l`. Protected presentation markers are skipped without consuming character or word counts. Every complete Opaque subtree is one word-motion unit for `w`, `b`, and `e`, regardless of its projection's internal words. `e` and `ge` move to word ends forward and backward. `gg` and `G` jump to the start and end of the entire structured Description document. `Ctrl+D` and `Ctrl+U` move the cursor by approximately one visible Task Detail Pane height. Visual Mode extends the selection with these motions; `o` swaps its active end and `Esc` cancels it.
35. `{` and `}` move backward and forward by paragraph-motion units; counts apply. Normal-mode `ö` and `ä` are German-keyboard aliases for `{` and `}`. Every navigable Description block is one paragraph-motion unit, including each heading, List or Checkbox-list entry, quote, rule, table, and complete Code block. A Code block remains one unit regardless of its internal source lines or blank lines; `j` and `k` navigate those Code lines locally. A quote likewise remains one unit for `{`/`}`, while `j` and `k` navigate its child blocks locally.
36. Code-block editing uses ordinary Description Normal and Insert modes rather than a separate mode. `Enter` in a Code block inserts a literal source line, and pasted text preserves all line breaks and whitespace. `Esc` only returns to Normal Mode.

## V1 structural decisions — Questions checkpoint

User feedback accepts Questions `L01`–`L12`, `Q01`–`Q04`, and `C01`, with the explicit amendments below. Later V2/V4 answers and accepted defaults are consolidated here. This is specification approval, not execution evidence or blanket acceptance of every corpus field. No questionnaire resume remains.

### Lists

- **L01 — Outdent:** move the selected entry/subtree immediately after its former parent. Following siblings from its old list become children of the moved entry, preserving document reading order; existing descendants stay with it. This intentionally can reparent unselected following siblings.
- **L02 — Indent with existing children:** append the moved subtree after the previous sibling's existing children; never replace or reorder those children.
- **L03 — Multiple siblings:** move a contiguous sibling range together under its unselected previous sibling, preserving their sibling relationship and order; do not form a new chain of selected entries.
- **L04/L05 — Selection and atomicity:** normalize selected parent/child overlaps to the highest selected subtrees, then require one contiguous sibling range under a common parent. Validate the whole operation before mutation. If the selection includes the first sibling (e.g. A and B together), there is no unselected preceding sibling to receive it: reject everything with a footer warning. Never indent only B or use selected A as an implicit receiving parent. Unsupported multi-depth selections likewise reject unchanged.
- **L06 — Types:** preserve the moved entry's list kind (ordered, unordered, Checkbox); create a valid matching container when required. Only explicit conversion changes kind; reject if safe representation is impossible.
- **L07 — Checkbox state/identity:** moves preserve IDs and checked states, recompute affected Checklist progress summaries, and never change Task Done.
- **L08 — Numbering:** preserve and render meaningful imported `start`, `reversed`, and `li value`. Entries without explicit values follow the destination list's numbering; do not silently renumber destination containers to preserve old display numbers. Split-list continuation follows L11.
- **L09 — Root outdent:** reject without mutation and show a hint; list-to-paragraph conversion is separate. No empty receiving parent or CSS-only indentation is synthesized.
- **L10 — Middle split (user amendment):** Insert Enter in `AlphaBeta` creates adjacent sibling entries `Alpha`, `Beta`, with existing child entries attached to **Beta**, not Alpha. This preserves text/child reading order despite changing the children's parent. Alpha retains its existing Checkbox ID/checked state; Beta is unchecked with a fresh save-assigned ID and receives the original children. Do not copy unique IDs. Unknown attributes must be allocated losslessly or the specific split is rejected.
- **L11 — Empty middle entry exit:** split the list into its preceding and following parts with a new empty paragraph between them. Preserve following entry order and explicit numbered continuation when safely representable; do not silently discard non-transferable attributes.
- **L12 — Merge compatibility:** automatic boundary merging requires the same block kind, compatible attributes, and compatible structural position. Otherwise reject unchanged with a hint. Ordinary paragraph merges still invent neither space nor hard break; quote boundaries remain protected.

### Quotes

- **Q01 — Local removal:** unwrap only the selected children at the applicable quote depth, splitting the container when needed; unselected neighbors stay quoted. Normal `Space+q` follows the same local scope.
- **Q02 — Shared wrapping:** a contiguous selection of sibling blocks gains one common new quote container, not one independent container per child. Verified shortcut: **V → motions → Space+w** adds a layer; **Space+q** in that palette removes a layer. Normal `Space+q` remains the quote toggle. Different-parent wrapping must not implicitly expand selection.

## First native editing set

V1 natively renders and edits:

- paragraphs and headings (`h1`–`h3`)
- bold, italic, underline, and strikethrough text
- inline Code spans: read, edit their text, create them, and remove their Code formatting in V1; existing safely understood `<code>` spans are Native rather than automatically Opaque. Single-backtick editor syntax is the intended creation/removal form; markup-looking text inside Code stays literal. Deliberately typed paired single backticks create Code; imported/pasted backticks remain literal. Escaped inner backticks are content, other markup stays literal, and removing Code formatting preserves text and other marks. New empty character pairs remain literal; imported empty semantic wrappers are removed. Ordinary text edits inside the span retain Code, while insertion exactly outside its boundaries remains outside, consistent with explicit edge handling; this is a derived implementation default, not a separate user vote. Unsupported attributes/structures retain their preservation rules.
- code blocks and block quotes
- unordered and ordered lists
- Checkbox lists
- links
- horizontal rules

Tables are initially opaque, with a readable terminal-table projection. Images are likewise readable but opaque: render `[Image: alt]`, falling back to `[Image: title]` or `[Image]`; M3 neither renders pixels nor uploads, edits, or replaces image metadata. Generic VOA Task Attachments are separate Task-level records rather than Description markup; only image attachments may also appear as `<img>` nodes. Existing VOA user mentions are readable opaque inline atoms rendered as `@label`, falling back to `@id`, with no M3 creation or internal editing flow. Imported embedded media (`iframe`, `video`, `audio`, `embed`, or `object`) is one atomic opaque `[Embedded media]` block. M3 does not introduce a generic attachment block in Descriptions; later Task Detail Pane attachment browsing/management remains open for separate evaluation. Each outermost opaque structure follows the global atomic preservation rules: ordinary edits preserve its complete original HTML byte-for-byte; focus and copy reveal only its safe projection, never hidden source URLs, IDs, attributes, or raw markup; formatting skips it; and complete deletion or replacement requires confirmation. Copying its safe projection and pasting creates native editable text, not a duplicate opaque structure. An unknown but safely parseable element with text content recursively contributes that text to the outermost opaque subtree's safe projection using known child semantics where possible; a structurally empty unknown element renders `[Unsupported content]`. Future Tiptap extensions remain opaque until their rendering and preservation behavior is specified.

Safe unknown attributes do not by themselves make a Native node opaque. Native nodes retain every safe unknown attribute by name and decoded value, while serialization may normalize attribute order, quoting, and equivalent entity spelling. A structural conversion carries safe unknown attributes onto the replacement element; if an attribute cannot be carried safely, the conversion is rejected rather than silently dropping it. The sole accepted exception here is explicit quote-layer removal with the Q03 metadata-loss confirmation; it does not authorize silent loss, Opaque rewriting, or attribute loss on other conversions. Duplicate attribute names on an otherwise Native element, compared case-insensitively, protect the smallest reliably bounded subtree as Opaque: preserve every original value/byte instead of choosing one recovered value. Only unreliable region boundaries can require wider blocking. Duplicate attributes inside an Opaque subtree remain part of its byte-preserved source and are not interpreted independently. An imported `style` attribute prevents its element from being Native: the outermost styled structure becomes an Opaque subtree whose original HTML is preserved exactly, while Vimkunja renders a safe projection and never applies the CSS. This avoids a security-sensitive CSS parser without discarding valid VOA formatting. Active content in or around that structure follows the same smallest-reliable-region protection rule; it is not executed and does not automatically block unrelated Native neighbors. An HTML comment is likewise one Opaque atom, rendered only as `[HTML comment]` without disclosing its contents. It is never preserved invisibly: users can focus it and use the ordinary confirmed Opaque deletion, replacement, Undo, and Redo flows.

## Native serialization contract

Native serialization preserves document meaning rather than source spelling. It may normalize tag form, attribute order and quoting, equivalent entity spelling, and whitespace that does not represent Description content. It must preserve meaningful text whitespace, Code-block contents, hard breaks, empty editable blocks, list structure, mark semantics and nesting depth, Link destinations and meaningful attributes, and Checkbox state and identity. It never substitutes visually similar but structurally different content, such as replacing `<br>` with a text newline. Contiguous top-level text and inline nodes in an otherwise valid imported fragment become one Native paragraph and serialize inside `<p>...</p>`; this is accepted structural normalization rather than malformed-HTML recovery. An empty Source HTML string remains an empty Description until the user creates content. Document-level markup such as `<!doctype>`, `<html>`, `<head>`, or `<body>` is invalid in a Description fragment and makes the Description Blocked; Vimkunja does not silently strip wrappers or rely on parser relocation.

Native text is serialized from decoded characters using one canonical HTML-escaping policy. Required escapes such as `&amp;` and `&lt;` appear only in persisted Source HTML; the Terminal projection continues to show decoded user-facing text. Unicode remains Unicode unless valid HTML requires escaping. Outside Code blocks and whitespace immediately beside imported hard breaks, runs of ordinary HTML-collapsible spaces, tabs, and source newlines in Native prose normalize to one visible separating space, and invisible collapsible whitespace at block boundaries may be removed. Non-breaking spaces and other non-collapsing Unicode whitespace remain distinct. Code-block text must be decoded from original source slices: the existing tokenizer's Token/Text normalizes CRLF to LF and cannot be used unchanged for this guarantee. CR, LF and CRLF delimit Code source lines, including CR-only terminal Paste; their bytes are preserved rather than normalized. Code-block text retains its exact decoded characters, including indentation, tabs, blank lines, and a final newline, even though characters that require HTML escaping are escaped in Source HTML.

Semantic round-trip tests aim to check every listed aspect of Native meaning: document structure, text, marks and their nesting, block boundaries, list and Checkbox state and identity, Links and their meaningful attributes, and exact decoded Code-block content. A check may be omitted when an exception makes it inapplicable. Tests ignore representation-only differences permitted above. Opaque-subtree checks verify exact original bytes after unrelated edits, including tag spelling, attributes, whitespace, children, and nesting, as well as retained identity, order, and parent position. Blocked Descriptions have no automatic-save or round-trip claim, and deliberately removed content is excluded from preservation checks.

Empty editable block positions remain structural content. Empty paragraphs serialize as `<p></p>`; empty headings, Code blocks, Block quotes, and individual list entries remain representable and persist. Deleting a list's final real entry removes its outer list or Checkbox-list container. An imported already-entry-less list is preserved, with a nonpersisted fill target; focus/canceled Insert does not synthesize a li. Empty imported semantic inline-mark wrappers are removed; newly typed empty delimiter character pairs remain literal text. An imported empty-label Link remains preserved under the Link rules, but Vimkunja does not create one. Vimkunja does not insert `<br>` merely to make an empty block visible in the TUI.

Canonical Native mark output is standards-aligned rather than based only on visual similarity. Newly applied bold, italic, underline, and strikethrough use `<strong>`, `<em>`, `<u>`, and `<s>`. Imported `<b>`/`<strong>` and `<i>`/`<em>` variants retain their distinct HTML semantics, including repeated `<strong>` or `<em>` depth. Only obsolete `<strike>` is normalized to `<s>`.

## Projection principle

> Friendly projection by default, source disclosure near the cursor.

The current logical block reveals its editable source syntax in Normal and Insert modes; cursor motions operate over the disclosed source characters. Away from the cursor, the user-friendly interpretation is rendered. This applies uniformly to headings, inline marks, and horizontal rules. A Code block discloses its entire canonical triple-backtick enclosure while the cursor is anywhere inside it, while retaining the background across the whole block. Real source Tabs display as a muted `>` followed by `~` to the next configured source tabstop (for example `>~~~` at column zero with tabstop 4); ordinary spaces stay blank. These display cells do not become extra cursor targets or copied/saved content. Its fences are a deliberate exception: they are protected structural markers, not cursor targets or editable content. Markdown-like delimiters are editor syntax only; persistence remains semantic Vikunja-compatible HTML.

Exactly three or four consecutive, directly typed backticks in an otherwise empty paragraph remain ordinary text until Enter confirms the trigger. Enter consumes the complete trigger, creates the same structured Code block, and places the cursor on an empty Code line between canonical triple-backtick fences. Six directly typed backticks in one otherwise empty paragraph also qualify when Enter is inserted exactly between the third and fourth backtick, consuming both groups and creating an empty Code block. Navigation to that boundary does not invalidate this paired trigger. Six markers at another cursor position, five/eight markers or additional text do not qualify. Paste and an escaped first marker never trigger conversion. Backspace edits the unconfirmed candidate normally; Esc only leaves Insert Mode. Confirmation is one draft Undo step. After conversion, a newly typed backtick is ordinary Code text. No timing heuristic is used, no fourth trigger character persists, and no HTML is exposed. Description Normal Mode Space+c provides direct Code-block creation without typing the trigger.

Lists use indentation and ordinary markers; Checkbox entries use `☐`/`☑`. Checkbox toggles never change the enclosing Task Done state. Historical entries without IDs remain editable and receive a lowercase UUID v4 on the next successful Description save. Quotes use their non-editable presentation prefixes rather than disclosed pseudo-Markdown syntax. Imported empty quotes render as one empty editable quoted line and are preserved on save; `Space+q` on an empty paragraph creates one. The Vimkunja Markdown-like markup dialect must be documented in Help and durable user documentation, and taught in a dedicated Vimkunja markup-tutorial section.

## Editor syntax and atomic presentation

These rules govern editor syntax, not Source HTML:

- `***text***` applies one bold and one italic layer and serializes as `<strong><em>text</em></strong>`; it does not encode repeated emphasis.
- Imported repeated semantic emphasis discloses nested delimiter pairs with protected b/strong or i/em variant labels at the midpoint between layers; ASCII separator |. Separators distinguish repeated layers from combined bold/italic, are not cursor targets, and are never persisted.
- A backslash escapes the next syntax character: backslash, `*`, `_`, `~`, backtick, `#`, `-`, `+`, `.`, or square bracket. Before other characters or at a block's end it remains literal. Escapes are editor syntax only; Source HTML stores the resulting literal characters. Existing unmatched, mismatched, or overlapping delimiter sequences remain literal. Ordinary periods in imported/pasted text display as periods even in the focused block, without synthetic backslashes or extra syntax cursor targets; this does not remove explicit typed backslash-period support.
- At a logical block's start, directly typed `# `, `## `, or `### ` creates a heading; `- `, `+ `, `* `, or `1. ` creates a list entry. These triggers require a following space. A dash-only line of at least three dashes creates a rule; retain its directly typed dash count in the draft for incremental x/Undo, canonicalizing to hr on save; exactly three or four directly typed backticks in an otherwise empty paragraph create a Code block only when confirmed with Enter; six directly typed backticks also create an empty Code block when Enter is inserted between the two groups of three. Escaping the first marker prevents conversion.
- Pasting never triggers structural conversion. Pasting `# Shopping` followed by `- Milk` creates two ordinary paragraphs containing those literal markers, not a heading and list.
- Protected markers (quote prefixes, Code fences, emphasis-layer separators) are skipped by motions and may be crossed by selections but are never copied, deleted, or formatted as text. Editable delimiters remain ordinary cursor targets.
- Opaque subtrees must visibly form atomic units, including when their safe projection contains multiple words or rows. Use enclosing brackets/outline plus subtle highlighting, with a non-color boundary cue and a marked multiline extent. Bracket style and highlighting color are configurable. The frame/color are configurable; exact rendering awaits practical checks; raw attributes remain hidden.

### One Description editor and shared system clipboard — user-requested follow-up

Every Description, including empty and legacy plain text, uses the existing Native document editor. There is no user-visible plain/rich mode switch or required conversion command. Legacy plain text enters the draft as literal paragraph content, one paragraph per line, with original source bytes retained as the persistence baseline. Reading, navigation, selection, resize and metadata-only saves do not rewrite it. Actual Description edits produce Native HTML; normal save, conflict detection, Undo/Redo and discard use the same path as HTML imports. Before save, Undo back to the starting nodes restores exact plain bytes. Imported/pasted syntax remains literal; deliberate typing uses Native syntax rules.

Title, Description and Comment drafts share Space+y (copy selection or current line; Description prose uses its logical paragraph) and Space+p (literal Paste at the cursor or replacement of the selection, remaining Normal). Link URL copying moves to Space+Y. Copy preserves text/selection; errors and empty Paste do not change them. Description bare y/p retains the local register. Title/Comments use one shared plain-text selection module; Description uses its structured selection engine for every source. Insert-only prompts retain their input rules. Clipboard reads capture their destination and reject stale results. This supersedes the earlier lowercase Link-copy shortcut, Plaintext Visual limitation and proposed explicit conversion command.

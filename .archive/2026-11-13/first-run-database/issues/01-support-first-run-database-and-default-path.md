# 01 — Support a fresh database and a default database path

**Phase:** M3 — first-run usability

**What to build:** Let a new installation start without an existing database or an explicit `--db` argument. Create a usable, empty Vikunja-compatible database, either by initializing it or by installing a validated starter template.

**Category:** enhancement

**Status:** completed

**Recorded:** 2026-10-23

## Behavior before implementation

`--db` already defaults to the working-directory-relative path `internal/db/vikunja.db`. This ignored local file is absent from a fresh clone. The Store deliberately opens existing files only (`mode=rw`), and production startup rejects missing or incompatible schemas. The tutorial creates disposable synthetic data; it is not a persistent production starter.

## Requirements

- [x] Start successfully on a fresh installation without supplying `--db` or preparing a database manually.
- [x] Provide a documented default database path; decide whether to retain the repository-relative default or use a platform user-data directory that also works outside the repository. Define how existing default databases are handled so an upgrade does not silently switch users to an empty database.
- [x] When the intended new database is absent, create it through a compatible initialization flow or a validated, distributed starter template. An empty SQLite file alone is insufficient.
- [x] Preserve Vikunja 2.7.0 schema and migration-history compatibility. Do not invent or modify the upstream schema, silently migrate existing databases, or relax existing compatibility checks.
- [x] Define the minimum local User, Project, and View setup needed for a usable start. Empty means no personal or demo Tasks; any required starter records must be deliberate and documented. Coordinate with [Project creation](../../../../.scratch/project-creation/issues/01-specify-project-creation-workflow.md).
- [x] Preserve explicit `--db` selection. Specify whether an explicitly supplied missing path is initialized or rejected, and how initialization intent is communicated.
- [x] Preserve existing databases byte-for-byte unless the user performs ordinary application edits. Reject invalid or incompatible existing files without replacing them.
- [x] Handle missing parent directories, permissions, partial initialization, and concurrent first starts without overwriting data or leaving an apparently valid partial database. Report the chosen path and actionable failures.
- [x] If using a template, define its generation, distribution, version validation, and license/provenance requirements. Exclude real user data, machine-specific paths, and demo content.
- [x] Add focused tests for fresh startup, repeated startup/data preservation, default and explicit paths, incompatible files, and initialization failures. Verify a newly created database with official Vikunja 2.7.0.
- [x] Update README installation/default-path guidance and CLI help to match the implemented behavior; keep tutorial data disposable and separate.

## Decisions before implementation

Jan accepted the proposed defaults and authorized implementation on 2026-11-13. The accepted contract and template provenance are recorded in [spec.md](../spec.md). Fresh default startup installs a validated template in the platform user-data directory; existing legacy defaults remain preferred. Explicit missing paths are rejected. The starter contains Local User, Inbox, four standard Views and three Buckets, with no demo Tasks or usable password.
